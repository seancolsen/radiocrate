# DML API

Implement a new API that allows making arbitrary changes to the database. This should be an RPC API with "dml" as the RPC method name.

## Product-level design philosophy

Collectune is supposed to be for the user to query their music collection and play music. But it's also supposed to be a powerful tool for _organizing_ a collection of music. That means modifying data too! Currently, the only data modification we support is CRUD on some specific entities like queries and presets. We need a new API to support arbitrary DML on _anything_ in the Collectune database. Collectune will have a powerful UI that allows the user to edit relational data from the query results view. The most common workflow will be: query tracks, edit a track. But the same functionality should work for other entities too.

My vision is that the schema structure of tables and columns that gets installed by collectune is simply a starting point for the user. If the user wants to add their own custom columns or tables, then Collectune will (eventually) be able to handle that. That's why we have very little in the way of ORM type logic in the backend. The frontend dynamically introspects the schema and then uses the structure to inform its queries. I would like for DML to work in the same manner. DML should begin with dynamic introspection, then dynamic UI form-building, then some form of very flexible API that allows for inserting/deleting/updating almost anything. Keep in mind: Collectune is designed to be a single-user multi-device application. The user "owns" this data. We want to give them a lot of power over it. But we also want to draw the line at some point by preventing them from _accidentally_ doing large destructive operations, or doing anything that would put the database into a corrupted state. Those are the high-level goals here.

In addition to inserting, deleting, and updating individual records, we'll also need the ability to do all of these operations in bulk. For example: the user might select 12 tracks, edit all of them in bulk, modifying track.genre (UPDATE), modifying album.year (UPDATE), removing a credit to a specific artist (DELETE), and adding a credit to a different artist (INSERT). We should perform all these operations in a single transaction, because there will be a single form driving this API with a single point of failure and recovery in the UI. We will _not_ need to update or delete records based on predicate conditions, e.g. `year < 1999`. Bulk operations will happen via loading records in the UI, selecting them, then passing all of their ids to the API for modification.

Also, writes will be very low-volume in this app. This is not the hot path! We are expecting a low number of operations per DML request (on the order of 10) and a very low frequency of DML requests (on the order of 10 per minute, peak). So it's okay if performance isn't fantastic on this API.

## RPC parameters

Example:

```json
{
  "jsonrpc": "2.0",
  "method": "dml",
  "params": {
    "operations": [
      {
        "id": "cqB5mPeyMhACfH91kIyN",
        "operation": "insert",
        "table": "artist",
        "values": {
          "name": "Beatles"
        }
      },
      {
        "id": "UByxhKfRB59PBipQSlVh",
        "operation": "insert",
        "table": "credit",
        "values": {
          "track": "d55b955b-6416-440d-bc12-9369c39806d0",
          "artist": {
            "id": "cqB5mPeyMhACfH91kIyN"
          },
          "ord": 1
        }
      },
      {
        "id": "fgFP2IfbAqUJiAWwhUSs",
        "operation": "insert",
        "table": "album",
        "values": {
          "title": "Abbey Road",
          "year": 1969
        }
      },
      {
        "id": "v2RVoydXxusq2SahS3OB",
        "operation": "update",
        "table": "track",
        "where": {
          "id": "d55b955b-6416-440d-bc12-9369c39806d0"
        },
        "values": {
          "genre": "Rock",
          "album": {
            "id": "fgFP2IfbAqUJiAWwhUSs"
          }
        }
      },
      {
        "id": "GucNNgWTq2romd4GGTzZ",
        "operation": "delete",
        "table": "credit",
        "where": {
          "id": "e7acb832-f3a8-4f08-826d-ad56244a8246"
        }
      }
    ]
  }
}
```

The parameters should have the following structure:

(I'm using TypeScript to spell this out, just because it's concise, not because we'll be using it for the implementation.)

```ts
interface Params {
  operations: Operation[];
}

type Operation = Insert | Update | Delete;

interface Insert {
  operation: 'insert';
  id: string;
  table: string;
  values: Record<string, Value>;
}

interface Update {
  operation: 'update';
  id: string;
  table: string;
  where: Record<string, Value>;
  values: Record<string, Value>;
}

interface Delete {
  operation: 'delete';
  id: string;
  table: string;
  where: Record<string, Value>;
}

// A static literal, or a reference to the record produced by a prior
// operation (only valid for foreign-key columns).
type Value = string | number | boolean | null | { id: string };
```

Notes:

- **Batching** Note that we're not relying on the batching mechanism built into the JSON-RPC spec. Instead, we're baking the batching into the parameters. This is to ensure that the batch runs within a single transaction and that all operations run in sequence.

- **Operation ids:** Operations are in a flat, ordered list. Each operation gets a unique string id, set by the client. The ids are semantically meaningless to the server. The server validates that ids are unique across all operations.


## Behavior

- At the start of every request to this new DML API, the backend should perform a full introspection of all database tables and columns.

    We already have almost everything we need for this introspection logic within Querydown's introspection query. You can find it in the Querydown repository. Querydown is a dependency of ours, and also code that we are maintaining separately. Inside the Querydown repo, the introspection SQL is at `compiler/resources/introspection/duckdb.sql`. You'll be able to view it but not modify it. Given that we need much of this functionality, plus a little more, I think we should probably just copy that SQL into a file in this repo and use it as a starting point. We have Querydown as a dependency already, but only on the front end. In the future perhaps we'll want a lower-level crate that holds only the introspection SQL, but I don't want to do that now.

    Querydown's introspection query already gives us most of the table/column
    structure, but this API needs three additional pieces of metadata that we'll
    have to extend it with (or derive alongside it):

    - **Nullability** — which columns are nullable vs. `NOT NULL`. Needed to
      validate inserts/updates and to reason about `where` clauses.
    - **Foreign-key / reference graph** — which columns reference which tables.
      Needed both to resolve operation-reference values (see below) and to run
      the delete dangling-reference check in both directions.
    - **Unique-constraint / primary-key metadata**, including multi-column
      constraints. Needed to validate that an `update`/`delete` `where` clause
      identifies exactly one row (see "Update behavior").

    It's possible we'll need even more introspection information as the
    implementation proceeds.

- Each API request should wrap all operations in a transaction. Roll back the transaction if we get any failures. In addition to committing the transaction, be sure to run a DuckDB checkpoint at the end.

    Currently, all DuckDB writes flow through `AppState::write`, which enforces
    the checkpoint invariant, but that utility runs its closure against a shared
    `&Connection` and does not open a transaction. DuckDB's `Connection::transaction()`
    requires `&mut Connection`, so we'll need a mutable write path (e.g. a
    `write_mut` variant that locks the mutex mutably, runs `BEGIN … COMMIT`
    inside the closure, then checkpoints once after commit). Note that a single
    DML request will hold the global DB lock for its full duration; that's
    acceptable given how low-volume writes are.

- In the parameters example, you can see that the inside the "values" object, we can have static values like strings and numbers — and for foreign key columns we can reference the result of a previous operation. For example, in our first operation we're inserting the artist "Beatles" and in our second operation we're inserting a credit for a previously-existing track to this newly-inserted artist. When we insert the artist, we need to get its id, and feed that id into the operation to insert the credit. This should only be possible for foreign key columns.

    Resolution rules for a `values` entry on a foreign-key column:

    - A **scalar** value (string/number/null) is used as a literal foreign-key value.
    - An **object** of the form `{ "id": "<operation-id>" }` is an
      operation-reference: the server resolves it to the `id` of the record
      produced by that earlier operation. References always resolve against the
      referenced operation's returned `id` column specifically.
    - A reference may only target an operation that actually produces a result —
      i.e. an `insert` or `update`. Referencing a `delete` (which is void) is an
      error.

- We should validate that a request has its operations ordered correctly. If any operation references an id that does not belong to a strictly preceding operation, this should be an error.


## Return value structure

Here's an example of a single successful insert...

- Request:

    ```json
    {
      "jsonrpc": "2.0",
      "method": "dml",
      "params": {
        "operations": [
          {
            "id": "cqB5mPeyMhACfH91kIyN",
            "operation": "insert",
            "table": "artist",
            "values": {
              "name": "Beatles"
            }
          }
        ]
      },
      "id": 1
    }
    ```

- Response

    ```json
    {
      "jsonrpc": "2.0",
      "result": {
        "cqB5mPeyMhACfH91kIyN": {
          "id": "34f218f8-4a1f-4342-854d-4b74b2b15eb6",
          "name": "Beatles"
        }
      },
      "id": 1
    }
    ```

Notes:

- The response provides a "result" object with keys corresponding to the operation ids and values corresponding to the return value for that specific operation.
- If an operation is void (e.g. delete), then the "result" object will not contain an entry for it.

## Insert behavior

- An insert should fail if any constraints fail, e.g. unique constraint violation.
- It should return the full object of the record that we just inserted, as returned from the database.

## Update behavior

- An update should fail if the request does not contain a "where" object that specifies a non-null unique constraint (most commonly a primary key, but possibly an alternate unique constraint). Note that some such non-null unique constraints are multi-column (e.g. in the "credit" table). We validate the columns named in "where" against the introspected unique-constraint metadata.

- An update that matches **zero rows** (e.g. a `where` id that doesn't exist) should fail, rather than silently succeeding as a no-op.

- The return value should be structured just like that of the "insert" operation.

## Delete behavior

- Should have a void return on success.

- Since we don't have real foreign keys in this database, the API is
  responsible for protecting referential integrity itself. But we deliberately
  keep this logic "dumb": the server does **not** cascade deletes or null out
  references. Instead, **a delete must fail if it would leave any dangling
  reference** — that is, if, at the moment the delete runs, any row in any table
  still has a non-null foreign-key column pointing at the record being deleted.

    It is the front end's responsibility to assemble the full deletion tree and
    express it as an ordered list of operations. For example, to delete an
    artist that has credits, the client sends `delete` operations for each
    referencing `credit` (ordered _before_ the artist delete), followed by the
    artist delete. To achieve "SET NULL" semantics (e.g. deleting an album that
    tracks reference), the client first sends `update` operations that set the
    referencing `track.album` columns to NULL, then the album delete.

    Because operations run in sequence within a single transaction, the
    dangling-reference check is evaluated against the live transaction state at
    the moment each delete runs. A reference from a row that a _preceding_
    operation already deleted (or already nulled out) is therefore not
    considered dangling. A reference from a row scheduled to be deleted by a
    _later_ operation still counts as dangling, so the client must order the
    tree leaves-first.

- Implementing this check requires introspecting the reverse foreign-key graph
  (which columns in which tables reference this table) — see the introspection
  requirements under "Behavior".

- Note that the app does have some entities which will require special attention when deleting. For example, when deleting a `file` record, we'll want to delete the underlying file from the file system and add a "deletion" record. We'll have an entirely separate API for this, so you don't need to worry about that special behavior. It's out of scope for now.

## Error behavior

On error, the top-level API return value should look like this:

```json
{
  "jsonrpc": "2.0",
  "error": {
    "code": 1,
    "message": "Duplicate key \"name: Beatles\" violates unique constraint.",
    "data": {
      "operation": {
        "id": "cqB5mPeyMhACfH91kIyN"
      }
    }
  },
  "id": 1
}
```

Notes:

- At `data.operation.id`, return the id of the operation that resulted in the error.
- In an error scenario, at maximum a single operation is relevant — the operation upon which we encountered the error. If we encounter an error during validation before running any operations, then the "data" property will be `null`.
- Use code = 1 for everything for now to represent an unknown error code. We may choose to add error codes in the future.
- **Implementation note:** the existing RPC error channel can't express this
  shape yet. `dispatch` returns `Result<Value, String>` and `RpcError` carries
  only `code` + `message`. We'll need to widen the error path so a handler can
  return a structured error (a `code` plus an optional `data` payload), and add
  a `data` field to `RpcError`. This is a small cross-cutting change to the RPC
  layer rather than something local to the `dml` handler.

## Testing

- Add tests for this API which run against DuckDB in memory.
- All tests should begin with a schema initialized using our migrations.
- Each test should have its own sample data on top of the schema, isolated to the test.

## Specific behavior to test

- When I try to delete an album that still has tracks referencing it, the delete is rejected (dangling reference).
- When I first update those tracks to set `album` to NULL and then delete the album — in the same request, ordered correctly — it succeeds.
- When I try to delete a file that a track still references, the delete is rejected. When the same request deletes the track first and then the file, it succeeds.
- When I delete an artist that has credits, ordering the credit deletes before the artist delete in one request, it succeeds; omitting the credit deletes causes the artist delete to be rejected.
- When I try to insert an artist with a name that already exists it should fail.
- When I try to update an artist using an id that does not exist, it should fail.
- When an operation references the result of a later (or non-existent) operation, the request is rejected during validation.
- When an insert references the id of a preceding insert on a foreign-key column, the reference resolves to the newly-created record's id.

Add other tests for behavior that you think is worthwhile to test.

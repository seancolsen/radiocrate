# Phase 04 — The real results grid, rendered as raw DOM (DOM/SolidJS)

## Where this fits (read first)

We are migrating RadioCrate's frontend from an **egui/eframe WASM canvas** app to
a **web-native SolidJS DOM** app, rebuilding the UI **from the outside in**. Prior
phases:

- **Phase 01–02 (done):** moved the egui app to `frontend-old-egui/`
  (read-only reference) and stood up a fresh SolidJS SPA in `frontend/`
  (Bun/Vite/Tailwind v4/ESLint+solid/Prettier/tsgo/Playwright), then built the
  app **frame** (explorer sidebar + tab bar). Tabs carry `{ id, name }`.
- **Phase 03 (done — [`phase-03.md`](phase-03.md)):** wired the full
  `definition → SQL → results` pipeline end to end and rendered results as
  **plain space/newline-joined text**. It added: the Querydown compiler binding
  (`querydown-js`, built from git at `aa4c06c`, vendored under
  `frontend/vendor/querydown-js/`, gitignored; regenerated by
  `cargo xtask build-release`), `apache-arrow`, the TS ports
  [`src/query/definition.ts`](../../frontend/src/query/definition.ts) (`assemble`
  + `PRELUDE`), [`src/query/schema.ts`](../../frontend/src/query/schema.ts)
  (introspection SQL + `addInferredLinks`),
  [`src/query/compile.ts`](../../frontend/src/query/compile.ts),
  [`src/api/query.ts`](../../frontend/src/api/query.ts) (`runSql` + Arrow decode +
  `tableToText`), the store's schema/presets resources + `runQuery` +
  `resultsByTab`, and [`QueryPage`](../../frontend/src/components/QueryPage.tsx) /
  [`QueryToolbar`](../../frontend/src/components/QueryToolbar.tsx) (refresh only) /
  [`QueryResults`](../../frontend/src/components/QueryResults.tsx) (the `<pre>`).
- **Phase 04 (this plan):** replace the plain-text results with the **real
  columnar results grid** as it appears in
  [`frontend-old-egui/tests/snapshots/app/whole_app.png`](../../frontend-old-egui/tests/snapshots/app/whole_app.png)
  — multi-column rows, artist **pills**, per-column fonts/colors/alignment,
  formatters, the subtle row sheen + separators. Render **every row directly as
  DOM nodes** (no virtual scroll window, no canvas). Expect ~10k rows. **Rendering
  and scrolling performance is the top priority** of this phase.

The `frontend-old-egui/` crate remains the **behavioral/visual source of truth**;
port behavior, not its immediate-mode Rust structure. All cited `file:line`
references point into it.

### Why this phase exists

The whole reason RadioCrate started on egui was fast scrolling over large result
sets on a canvas. This phase deliberately throws all rows into the DOM — **no
virtual scrolling, no canvas** — to get an honest baseline of how a pure-DOM grid
actually performs at ~10k rows, after a genuine best effort at making it fast. If
DOM scrolling is acceptable, we avoid a virtualization layer entirely; if it
isn't, we'll have measured proof and can add windowing later. **Do not add a
virtual scroll window in this phase** — that would defeat the measurement.

### Stack recap (unchanged)

SolidJS (**not React** — see the "Writing SolidJS" block in
[`CLAUDE.md`](../../CLAUDE.md)) · Bun · Vite + `vite-plugin-solid` · Tailwind v4 ·
`tsgo`/ESLint(+`eslint-plugin-solid`)/Prettier · Playwright full-page snapshots
(light + dark). Pure JS — **no `Cargo.toml`, no `duckdb-sys`/cargo build-cost
rules apply.** Run the Bun/Vite/lint/test commands freely from `frontend/`. This
phase adds **no new runtime dependencies** (the compiler binding and
`apache-arrow` are already in place; no date library — see §3.3).

## Goal & scope

Render the current tab's result set as a columnar DOM grid matching
`whole_app.png`, with every row present in the DOM, tuned for scroll/render
performance.

### Do

1. **Port the field-layout algorithm** (`frontend-old-egui/src/field_layout.rs`)
   to TypeScript, verbatim in behavior, and **memoize** it so query refresh and
   window resize don't recompute it needlessly (§3.1).
2. **Port per-column display metadata** (`columns.rs`) and the **formatters**
   (`format.rs`) so cells render with the right widths, fonts, colors, alignment,
   prefixes/suffixes, and value formatting (§3.2, §3.3). Feed the compiler's
   **`columnAnnotations`** (already returned by `querydown-js`, ignored in phase
   03) into this.
3. **Render each row with absolute-positioned cells** at a **fixed row height**,
   both derived from the memoized layout. **No CSS flex or grid** for the field
   layout — cells are absolutely positioned within the row (§4).
4. **Render all rows into a single scrollable area** as raw DOM, and make it as
   fast as you reasonably can (§5 is the heart of this phase).
5. **Match `whole_app.png` near pixel-for-pixel** — this is a primary goal, not a
   nice-to-have. Reproduce the row background sheen, bottom separators, artist
   **pills** (cream/brown, exact padding/radius/gap/font), small/light secondary
   columns, right-aligned durations/ratings, the `#`-prefixed track number,
   column widths, and vertical rhythm. Use the constants in §2 verbatim and the
   measurement tooling to tune font/line heights against the snapshot (§4).

### Do NOT implement (explicit non-goals)

- **Hover styling** on rows or pills.
- **Row selection** (click/shift/cmd selection, selection background, keyboard
  row navigation). Skip `handle_row_click` / `select_row_delta` entirely.
- **Context menu** on rows (the "Edit {base}" popup).
- **Double-click to play** tracks.
- The **now-playing row marker / accent bar** and the **unsaved-edits marker**
  (`is_current`, `unsaved` in `draw_row`) — no playback or record editor yet.
- **Primary-key / track-id column analysis** (`track_id_column`,
  `record_id_column`) — only needed for the features above.
- **A virtual scroll window / row recycling.** Render every row. (Off-screen
  *skipping* via `content-visibility` is encouraged — see §5 — that is not
  virtualization; the nodes still exist.)
- **A performance benchmark harness** — no synthetic large-dataset generator, no
  `?gridRows=` seam, no timing/FPS instrumentation. The user does the scale
  testing. Just implement thoughtfully (§5).
- The **`fit_pills` "+N" overflow bubble** and per-pill truncation (§4). Browser
  layout + cell clipping only.
- Any **query-editing UI**, error UI, or empty-state polish beyond what phase 03
  already has (keep console-only error handling; a bare "No results" is fine).

## 1. The pipeline you're extending

Phase 03's `runQuery` already: `assemble` → `compile`/`compile_sections` → `POST
/api/query` (raw SQL) → `tableFromIPC`. Two things change here:

- **Stop discarding `columnAnnotations`.** `querydown-js`'s `CompileResult` is
  `{ sql: string; columnAnnotations: (AnnotationValue | null)[] }`. Phase 03 read
  only `.sql`. Now return both from
  [`compile.ts`](../../frontend/src/query/compile.ts) and thread the annotations
  through to the renderer. They are **positional, one per output column**, aligned
  with the Arrow result's columns.
- **Store structured results, not text.** Replace the per-tab `string` with a
  decoded result (the Arrow `Table` + resolved `ColumnMetadata[]` + precomputed
  cell strings). See §6.

The backend and the whole `definition → SQL` path are unchanged. Do not touch
`backend/` or the Rust query pipeline.

### 3.1 `src/query/fieldLayout.ts` — the layout algorithm

### 3.2 `src/query/columns.ts` — column metadata

Port `ColumnMetadata` + `from_meta`. The input is one `AnnotationValue | null`

- `hide: raw.hide === "yes"`

Unknown keys ignored; a non-object annotation → all defaults. Port the tests.

### 3.3 `src/query/format.ts` — formatters

Port the four `Formatter` variants and `format(value) → string | null`

note any deviation in a comment. Port the `Number`/`Duration` tests exactly;
approximate the timestamp tests as the `Date`-based implementation allows.

`display_text(meta, value)` (from `results.rs:644`): apply the formatter (falling
back to the raw value), then wrap with `prefix`/`suffix`. Put this helper here or
in the renderer.

Extend the phase-03 module. You need, per result column: whether it's a **list**

## 4. The row DOM: absolute cells, fixed height (no flex/grid)

Reproduce `row_metrics` + `draw_row` as DOM. Compute the **row-independent
layout once** per (column-set, available-width):

1. **Visible columns:** the result columns whose `ColumnMetadata.hide` is false,
   each paired with its original column index (needed to read the right Arrow
   column). Their `ColSize`s (from `min_width`/`max_width`) feed the layout.
2. **`avail` width** = scroll-container content width − `TEXT_PAD_X * 2`.
3. **`computeFieldLayout(colSizes, avail, COL_GAP)`** → placements + line count.
4. **Per-line heights:** for each visible column, its font content height
   (normal vs small — see below) plus `PILL_LINE_EXTRA` if it's a list column;
   each line's height is the max over its columns. **Cumulative line tops** drive
   vertical placement. `row_height = sum(lineHeights) + ROW_PAD_Y * 2` (empty
   layout ⇒ one body-height line).

**Font heights.** egui uses `TextStyle::Body`/`Small` heights. In the DOM, pick
two fixed per-line content heights — e.g. **body ≈ 18px, small ≈ 15px** — as the
inputs to step 4, and set the matching cell `font-size` / `line-height` in CSS.
Keep them as named constants and **tune them against `whole_app.png`** (see the
measurement tooling in [`CLAUDE.md`](../../CLAUDE.md) / `DEVELOPMENT.md`:
`scripts/measure_snapshot.py`, PPP = 2). Hardcoding the heights (rather than
measuring the browser font per frame) keeps the layout deterministic and cheap to
memoize.

**Row markup (per row):**

- A row element of fixed height (`--row-h`), `position: relative`, `overflow:
  hidden`, with the vertical sheen as a `linear-gradient(--row-bg-top → --row-bg-bottom)`
  background and a 1px bottom separator (a `box-shadow`/`border-bottom` in the
  softened `--edge` color, or an inset gradient — match `draw_row`'s pixel-snapped
  separator closely enough).
- One **cell element per visible column**, `position: absolute`, with
  `left`, `width`, `top`, `height` taken from the placement/line (see §5 for how
  these are delivered via CSS variables). Cell text: `white-space: nowrap;
  overflow: hidden; text-overflow: ellipsis; text-align: <align>;` and
  `line-height` = the line's height so single-line text is vertically centered.
  Apply `font-size` (normal/small) and color (default `--ink` / light
  `--ink-weak`).
- **Pill cells** (list columns): render each element as an inline-block **pill**
  span (cream/brown `PILL_BG`, radius, `PILL_PAD_X/Y`, `PILL_GAP`) inside the
  cell box, `white-space: nowrap`, letting the cell's `overflow: hidden` clip
  overflow. Vertically center the pill row within the line. **Inline-block flow is
  neither flex nor grid — that's allowed** (the no-flex/grid rule is about the
  *column* layout within a row). **Do not port `fit_pills` / the "+N" overflow
  bubble.** It requires per-pill text measurement (`canvas.measureText`) on every
  pill cell — real complexity and cost for a case the reference snapshot doesn't
  even show (its pills fit). Let the browser lay pills out and the cell clip any
  overflow; that keeps this simple and fast, which the user explicitly wants.

**Loading state** (optional, cheap): phase 03 keeps the previous results while a
query reruns. egui greys all text to a uniform loading color while `running`. You
may apply a single `.loading` class on the container that overrides cell color;
it's not required for this phase.

## 5. Performance — think critically while implementing

At ~10k rows × ~8 visible cells this is ~**90k nodes** in the DOM at once. The
user runs the actual performance testing themselves against real data — **you do
not build a synthetic dataset, a measurement harness, or a benchmark.** Your job
is to *implement thoughtfully* so the raw-DOM grid has the best shot at scrolling
smoothly, rebuilding quickly on refresh, and repositioning cheaply on resize. Bake
in the levers below (roughly in priority order); don't add machinery to measure
them.

1. **`content-visibility: auto` per row**, with `contain-intrinsic-size: 0
   var(--row-h)`. This is the single biggest win: the browser skips layout/paint
   for off-screen rows while keeping them in the DOM and preserving correct scroll
   height. It does **not** virtualize (nodes still exist) — exactly the honest
   "all rows in the DOM, but fast" approach the user wants. Rows also get
   `contain: layout style paint` implicitly.

2. **Encode the layout in CSS custom properties on the scroll container; make
   cells read them.** For each visible column index `k`, maintain four vars
   `--cx-k / --cw-k / --ct-k / --ch-k` (left, width, top, height), plus a single
   `--row-h`. Every cell uses `left: var(--cx-k); width: var(--cw-k); top:
   var(--ct-k); height: var(--ch-k); line-height: var(--ch-k)`. Then:
   - **On resize:** recompute the (memoized) layout and **write only these ~
     (4·columns + 1) variables** on the container. The browser repositions all
     90k cells via CSS-var inheritance — **no per-node JS, no DOM rebuild.** This
     is how you make resize performant without touching the rows. Drive it from a
     `ResizeObserver` on the container, coalesced with `requestAnimationFrame`.
   - **On refresh (new data):** rebuild the rows; recompute the layout vars for
     the (possibly new) column set.
   Because a column keeps its index across resizes (only its x/width/line change),
   the cell nodes never change on resize — only the vars do.

3. **Build rows without per-row reactivity.** The result set is an immutable
   snapshot, so don't pay Solid's fine-grained-reactivity cost 10k times. Build
   the rows **imperatively** — construct an HTML string (escape cell text!) and
   assign `innerHTML` once, or build a `DocumentFragment` with `createElement` in
   a tight loop — inside an effect/`onMount` that re-runs when the tab's result
   data changes, mounting into a `ref`'d container. This gives the truest raw-DOM
   baseline and the fastest creation. **Deliberately avoid `<For>`/`<Index>` for
   the rows** (note this in a comment); reserve Solid reactivity for the container
   and toolbar.

4. **Minimize nodes and per-cell cost.** One element per scalar cell. Precompute
   all cell strings once (§3.4). Avoid inline styles that vary per cell (put
   varying geometry in the shared CSS vars keyed by column index; only text
   content and the column-index class differ per cell). Prefer a class like
   `c{k}` selecting the geometry vars over writing four inline styles per cell.

5. **Contain the scroll container** (`contain: strict` or at least `layout
   paint`) and give it `overflow: auto`. Avoid box-shadows/filters that force
   expensive repaint on scroll (the row sheen is a cheap gradient — fine).

6. **Don't re-stringify or re-layout on scroll.** Scrolling must touch nothing in
   JS. No scroll listeners driving rendering (that would be virtualization).

**No benchmarking harness.** Do not add a synthetic-dataset generator, a
`?gridRows=` seam, timing instrumentation, or an FPS counter. The user measures
performance on their own with real data. Keep the code free of measurement
scaffolding — apply the levers above and stop there.

## 9. Gotchas & notes

- **Absolute cells, not flex/grid.** The column layout is `left/width/top/height`
  per cell from the memoized `FieldLayout`. Delivering that geometry via
  container-level CSS variables (keyed by column index) is what makes resize
  cheap — don't write per-cell inline geometry that you'd have to rewrite on every
  resize.
- **All rows in the DOM is the spec.** `content-visibility: auto` is allowed (and
  encouraged) — it skips *painting*, not existence. A virtual scroll window / row
  recycling is **out of scope**; adding it would defeat the purpose of the
  experiment the user wants to run.
- **Don't pay Solid reactivity per row.** Build rows imperatively; the data is an
  immutable snapshot. Escape cell text if you build HTML strings.
- **`columnAnnotations` drive everything visible** — widths (min/max), fonts,
  colors, alignment, prefixes/suffixes, formatters, and which columns are hidden.
  A hidden column (`hide:"yes"`, typically the id column) is dropped from the
  visible set but still occupies a result-column index — read Arrow columns by the
  original index, not the visible position.
- **List columns → pills**, detected from the **Arrow type**, not from
  annotations. Inline-block pills clipped by the cell's `overflow:hidden` — no
